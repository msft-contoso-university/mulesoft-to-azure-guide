01 / Separate the Migration Decisions

Move the gateway, the integrations, and the backend APIs deliberately.

A MuleSoft migration can include API gateway policies, integrations implemented in Mule, and backend applications hosted elsewhere. Inventory these separately. An existing backend may only need new gateway routing; Mule-hosted business logic needs a new implementation or runtime. Select networking, regions, availability, and observability against your own requirements.

GATEWAY

Protect and expose APIs

Azure API Management handles gateway policies, access controls, quotas, API products, and developer access. It does not execute Mule applications or replace a general-purpose integration runtime. [1]

RUNTIME

Execute the integrations

Logic Apps handles visual orchestration. Functions or containerized services handle code-heavy work. Service Bus and Event Grid handle different messaging patterns. There is no single product that is all of Anypoint. [2]

AUTHORING

Define what low-code means

Visual API-backed workflows, employee approvals, visual data mapping, and business applications are different needs. Logic Apps, Power Automate, and Power Apps are complementary, not interchangeable. [3]

Migration principle: Keep gateway migration, integration-runtime migration, and backend API modernization as linked but distinct workstreams. Inventory dependencies and prove representative workloads before estimating the full estate.

03 / What Does Low-Code Actually Mean?

Choose the builder experience by audience and workload.

Low-code reduces the amount of hand-written orchestration. It does not remove the need for API design, testing, version control, identity, or production operations. Microsoft distinguishes Logic Apps from Power Automate by intended users and scenarios. [3]

Enterprise Integration

Logic Apps Standard

Who: integration specialists and professional developers.

Build: visual workflows, connector integrations, stateful processes, API-backed orchestration, B2B.

Experience: Azure portal and Visual Studio Code; workflow artifacts in source control.

Boundary: complex transformations, custom protocols, and specialized compute may still need code. Managed connector traffic does not automatically inherit a private network path.

Explore the runtime options
Business Automation

Power Automate

Who: business technologists and automation teams, with IT governance.

Build: approvals, employee workflows, Microsoft 365/SaaS automation, desktop RPA.

Experience: browser-based cloud-flow designer; desktop-flow tooling for RPA.

Boundary: licensing, platform request limits, DLP, owner/service-account lifecycle, environments, and solution-based ALM all matter.

Licensing and governance sources [18]
Business Applications

Power Apps

Who: app makers and application teams.

Build: forms, task screens, operational apps, Dataverse-backed experiences.

Experience: canvas or model-driven app authoring; connectors to governed services.

Boundary: this is the user experience layer, not the middleware engine. Put reusable integration logic behind appropriate services.

Power Apps overview [20]

Visual API development is not the same as API design.

For an HTTP-triggered process, Logic Apps can visually implement the backend workflow and APIM can expose and govern it. For a contract-first API, teams still design and version the OpenAPI definition and validate the implementation against it. Power Apps builds the user interface; it does not generate the full enterprise integration platform. MuleSoft API-design artifacts need their own conversion and review path. [5] [39]

Clarify the requirement: Is the desired experience a visual flow designer, a reusable connector catalog, a visual transformation mapper, a browser-based API contract editor, or all of these? Microsoft covers these through different tools rather than one Studio/Exchange-style surface.

Find a starting point

A discussion aid, not an automated architecture assessment. Select the dominant need, then validate the recommendation against security, scale, latency, and operational requirements.

Important distinction: APIM can import and expose an API; it does not implement the backend business process. A Logic Apps HTTP-triggered workflow can implement an API-backed process, but contract design, authentication, synchronous timeout limits, schema validation, and testing still need explicit attention.

04 / Service Deep Dives

Understand each service's job and its limits.

Select a service for practical fit, authoring experience, and migration implications. These services compose into a platform; they are not competing answers to the same question.

Primary Low-Code Runtime Candidate

Azure Logic Apps

Why it maps to Mule flows

  • Visual triggers, actions, conditions, scopes, loops, and connectors.
  • Standard supports multiple workflows in one resource, with stateful or stateless execution choices.
  • Stateful workflows persist execution state; stateless workflows favor shorter in-memory execution. Select deliberately rather than using one model everywhere.
  • Data Mapper can reduce hand-written transformation work for supported schemas; complex mappings still need expressions or code.

Standard vs. Consumption

  • Standard: single-tenant runtime, compute-based hosting, VNet integration/private endpoint options, local development, and project-based deployment. Managed connectors can add separate usage charges.
  • Consumption: multitenant service, one workflow per resource, primarily execution-based billing; a strong option for suitable intermittent workloads.
  • Connector availability, limits, networking, artifacts, and cost differ. Standard is a candidate for this estate, not an automatic winner.

Data Mapper: a useful visual tool, not DataWeave parity

The documented authoring experience is VS Code on Windows, for Standard projects, not the Azure portal or Consumption. The generated code pane is read-only; CSV schemas are not supported. Data Mapper maps use the Transform using Data Mapper XSLT action, which is not interchangeable with the separate Transform XML action. The documentation also lists string-filter comparison limitations. Inspect array-item mappings and test transformation results rather than assuming the visual map is complete. [8]

Pilot proof: one synchronous connector flow, one asynchronous failure/replay flow, and one difficult DataWeave mapping. Measure behavior, throughput, latency, private connectivity, run-history sensitivity, deployment, and support effort. [6] [7] [8]

Gateway, Not Integration Runtime

Azure API Management

Define the gateway workstream

  • Publish APIs and products; apply authentication, token validation, quotas, rate limits, routing, and bounded transformations.
  • Govern APIs hosted on Azure, on-premises, or elsewhere, including Mule-hosted backends during coexistence.
  • Use revisions/versions and a controlled policy pipeline; migrate client access and identity explicitly.
  • Validate consumer contracts, backend TLS, mTLS termination points, forwarded identity, and firewall paths through the selected edge and network controls.

Do not transfer classic assumptions to v2

  • APIM Premium classic and Premium v2 are different platform choices, not identical deployment models.
  • Recheck current tier support for multi-region gateways, zones, networking, capacity, and migration paths before committing.
  • Gateway multi-region availability is not the same as a multi-region control plane, nor does it replicate backend state or workflow execution.
  • Configuration and regional policy behavior, subscription keys, propagation, and recovery must be tested; do not equate a global entry point with end-to-end DR.

Governed Business Low-Code

Power Automate and Power Apps

Where they add value

  • Use Power Automate for employee-driven approvals, Microsoft 365 workflows, SaaS automation, and RPA.
  • Use Power Apps for user interfaces and operational applications that consume governed APIs.
  • Expose reusable enterprise capabilities through APIs rather than duplicating integration logic across many business flows.
  • A Composer migration may fit Power Automate conceptually, but connectors and flow behavior still require redesign.

Production governance is not optional

  • Set environment strategy, maker roles, connector data policies, and ownership/support arrangements.
  • Use solutions, connection references, environment variables, reviews, and deployment pipelines where supported.
  • Validate premium/custom connector licensing and service/request limits. An existing Microsoft 365 license is not blanket entitlement.
  • Check private access and gateway options per connector. Do not assume Azure VNet behavior applies to Power Platform.

Keep Code Where Code Helps

Functions and Container Apps

Azure Functions

  • Event-driven functions for custom transformations, validation, and focused integration logic.
  • Durable Functions provides code-first orchestration patterns when developers need that model.
  • Choose hosting based on networking, scale, execution duration, language, startup behavior, and operational needs.
  • Keep business logic testable and independent of gateway policies.

Azure Container Apps

  • Host containerized APIs, workers, and jobs with managed application infrastructure.
  • Useful for existing libraries, custom runtimes, and complex integration components.
  • Requires container engineering, image security, dependency ownership, and workload-level resiliency design.
  • Not a license-free Mule runtime replacement and not a visual integration designer.

Separate Commands, Events, and Streams

Service Bus, Event Grid, and Event Hubs

Service Bus

Durable enterprise commands, queues, and topic subscriptions. Use sessions for related ordered processing when required. Design lock renewal, dead-letter operations, duplicate handling, and replay.

[15]

Event Grid

Distribute notifications about things that happened. Handlers must accommodate delivery semantics; ordering and single delivery are not assumptions to build on.

[16]

Event Hubs

High-throughput event streaming with partitions and consumer offsets. Choose it for telemetry and streaming pipelines, not as a generic business work queue.

[17]

Shared rule: Persistence alone does not guarantee exactly-once business processing. Define idempotency keys, correlation IDs, retry budgets, dead-letter ownership, replay authorization, and retention.

Discovery Across the Estate

Azure API Center

What it contributes

  • An inventory for API discovery, metadata, definitions, versions, and governance across environments.
  • A way to catalog both migrated APIs and APIs still running on other platforms.
  • A complement to runtime gateway governance, not an additional gateway hop.

What it does not replace

  • APIM request execution, authentication enforcement, and runtime gateway policies.
  • The full Anypoint Exchange asset marketplace and all its reusable Mule artifacts.
  • Source control, package registries, schema repositories, and deployment pipelines.

05 / Composed Reference Architecture

One governed front door. Several execution patterns.

An illustrative pattern, not a prescribed topology. The diagram separates the request path from asynchronous processing and cross-cutting controls. Each required region needs its own runtime and data-recovery design. Retain or replace existing edge services based on requirements, not the migration label.

Regional HA is not whole-platform DR

Select regions and the APIM tier against business requirements. Specify RTO/RPO for workflows, messages, state stores, certificates, configuration, and backend systems separately. Prevent duplicate scheduled work and split-brain side effects.

APIM gateway failover does not recover in-flight Logic Apps executions or replicate application databases. Exercise failover and failback with realistic traffic. [25]

Private access is an end-to-end property

Trace inbound and outbound traffic through edge controls, firewalls, APIM, each runtime, connector infrastructure, DNS, and on-premises backends. An APIM private path does not make every connector private.

Separate network reachability from authorization. Check managed identity support, certificate rotation, service identities, and sensitive payload retention. [7] [22] [41]

06 / Backend API Migration

Move the implementation, not just the API URL.

First identify what MuleSoft owns: the API facade, business logic, orchestration, data access, or all four. Importing a definition into APIM does not move its implementation or data. Preserve a working consumer contract while you modernize the backend behind it. [44] [45]

REPOINT

Existing independent API

If a working Java, .NET, Node.js, or other service sits behind Mule, keep it where appropriate and change the gateway route first. Hosting migration can happen separately.

Validate network reachability, upstream/downstream identity, headers, timeouts, and error handling. Do not rewrite a stable service merely because its gateway changes.

REIMPLEMENT

API implemented in Mule

Extract the business behavior from Mule flows, DataWeave, connectors, policies, and shared modules. Rebuild that behavior in Logic Apps or code, then run consumer contract and regression tests.

The Migration Agent is an accelerator for supported artifacts, not a translator for every Java library, API specification, or runtime dependency.

REFACTOR

API plus long-running process

Separate fast request validation from durable processing when the business process exceeds the synchronous latency budget.

Where consumers support it, use an accepted response, a job/status resource, and an asynchronous worker. An HTTP 202 design is a contract change, not a transparent gateway migration. [46]

Build an API migration contract pack

  • Inventory OpenAPI/RAML, routes, verbs, schemas, versions, errors, pagination, and payload limits.
  • Record each consumer, credential/token model, authorization rule, certificate, IP dependency, and deprecation obligation.
  • Capture golden requests/responses and negative cases, including headers, precision, dates, optional fields, and retry behavior.
  • Map database calls, stored procedures, file access, downstream APIs, libraries, and transactional boundaries.
  • Set explicit throughput, percentile-latency, availability, RTO/RPO, and ownership targets.

Make cutover reversible

  • Keep the external hostname/path stable where feasible; validate DNS, TLS, caching, and token audiences explicitly.
  • Version incompatible changes and give consumers a transition plan.
  • Use controlled route changes, health checks, and representative load tests; verify feature support for the selected hosting tier.
  • Drain in-flight work and coordinate message-consumer ownership. Never blindly shadow production writes.
  • Test data/schema backward compatibility and define a rollback trigger, decision owner, and rollback window.

Data migration is its own workstream: A gateway rollback cannot undo writes made by a new backend. Plan database schema compatibility, state ownership, reconciliation, retention, and recovery separately from API routing. Move a service and its data together only when the dependency and downtime analysis justify it.

07 / Discovery, Acceleration, and Controlled Migration

Use automation to accelerate. Use tests to accept.

The useful first deliverable is an assessed workload inventory and a measured pilot, not a claim that every Mule flow converts to Logic Apps.

Migration Accelerator / Validate Current Coverage

Azure Logic Apps Migration Agent

Microsoft documents a VS Code extension powered by GitHub Copilot and the VS Code Language Model API, with five stages: discovery, planning, conversion, validation, and deployment. The target is Logic Apps Standard, not Consumption. MuleSoft support is relevant to this assessment, but generated analysis, workflows, connections, configuration, and code still require engineering review and behavioral validation. [27]

Evaluate with a representative project

  • Start from approved project files and environment requirements, not production credentials or unrestricted sensitive payloads.
  • Review the discovered inventory and migration plan before accepting conversion decisions.
  • Inspect generated workflows, mappings, connector bindings, code, deployment assets, and warnings.
  • Review the tool's prerequisites, model access, data handling, and current documentation before granting access to source.

Do not promise full automation

  • Mule version, parser coverage, connector coverage, and custom components affect feasibility.
  • DataWeave discovery does not prove semantic equivalence of the generated transformation.
  • API specifications and client migration remain a separate workstream where unsupported.
  • Validation must include contracts, failure behavior, security, performance, operations, and rollback, not only whether the generated project deploys.

Documented coverage at this snapshot: Version 1.12.1 includes Mule 4 project, flow, and DataWeave parsers; Mule 3 is supported with limitations and may require additional transformations. RAML and OpenAPI specification parsing is not implemented in that version. Treat contract conversion/import and client migration as separate workstreams. Parser support is not a guarantee of connector coverage or correct conversion of every expression. Recheck the installed release before the pilot. [27]

Tooling prerequisites and acceptance

The quickstart lists an Azure subscription, a GitHub Copilot subscription, Azure CLI, VS Code 1.85.0 or later, Migration Agent and Logic Apps Standard extensions, Azure Functions tooling/Core Tools, and Docker Desktop. Requirements can change between releases; check the complete current quickstart before setup. Obtain approval for source-code/model access and data handling; this guide does not assert a tool-specific privacy or residency guarantee. [30]

The documented validation stage exercises success and failure behavior and produces a TEST-REPORT.md. Review field-level outputs and the required test results before deployment. An agent-created report complements, rather than replaces, your engineering acceptance gates below. [31]

  1. Discover

    Export applications, APIs, flows, versions, connectors, DataWeave, policies, queues, schedules, test suites, deployment topology, and dependencies.

    Exit: an owner-approved inventory with sensitive-data classification and traffic baselines.

  2. Classify

    Place workloads into gateway-only, low-code integration, custom code, messaging, B2B/file, bulk-data, or retire/consolidate categories.

    Exit: target hypotheses, complexity bands, dependencies, and explicit unknowns.

  3. Pilot

    Use one simple flow and one difficult flow, including transformation and failure paths. Evaluate Migration Agent coverage on approved inputs.

    Exit: measured functional equivalence, operational readiness, and a revised estimate.

  4. Industrialize

    Build reusable identity, connectivity, connector, observability, testing, IaC, and deployment patterns. Define ownership and support runbooks.

    Exit: repeatable, reviewable deployments with rollback.

  5. Coexist and Cut Over

    Apply the incremental strangler pattern with APIM routing for API-by-API migration. Compare safe reads or sanitized replays; do not blindly mirror writes. Control queue consumer ownership. [40]

    Exit: approved wave criteria, consumer readiness, and a rehearsed rollback window.

  6. Retire and Optimize

    Remove unused Mule workloads only after dependency verification, retention needs, business acceptance, and licensing/contract review.

    Exit: decommission evidence, stabilized operations, and measured cost baselines.

Pilot acceptance must prove behavior, not just deployment.

Workload arithmetic before pricing

An illustrative 1,000,000 runs/month with 8 billable non-connector operations/run, 4 billable connector units/run, and 5% execution overhead produces 8,400,000 operation units and 4,200,000 connector units.

This is an assumption, not a production baseline. For Standard built-in operations, enter a zero per-operation rate and include hosting in the baseline. Model each managed connector category separately when rates differ.

For Consumption, a connector unit here means a billable execution; for Standard it means a billable call. Use observed metering, not a presumed one-action/one-call relationship. [49]

Build comparable scenarios

  • Baseline: current platform costs and business performance, including operations and license renewal dates.
  • Target: matching production capacity, recovery requirements, dev/test, support, and retention.
  • Transition: target run cost plus remaining Mule cost, temporary infrastructure, and migration labor.
  • Sensitivity: low/expected/peak traffic, connector fan-out, retries, log growth, and longer coexistence.

Use the Azure Pricing Calculator and negotiated rate sheets for a formal estimate. Record the region, currency, pricing date, discount assumptions, and exclusions.

09 / Discovery and Migration Readiness

Turn the inventory into an executable migration backlog.

Discovery checklist

Use during assessment and planning. Checkmarks are temporary to this open page and are not saved or transmitted.

Minimum inventory record per workload

  • Business purpose, technical owner, support team, criticality, consumers, and data classification.
  • Source product/version/hosting, API definition, implementation repository, test assets, and deployment pipeline.
  • Connectors, transformations, queues, schedules, libraries, certificates, credentials, and upstream/downstream dependencies.
  • Normal/peak traffic, payload distribution, latency targets, failure/retry profile, and recovery requirements.
  • Proposed disposition: retain/repoint, reimplement, refactor, consolidate, or retire; target hosting and unresolved gaps.
  • Complexity, effort confidence, cost assumptions, dependency order, acceptance tests, cutover plan, and rollback owner.

Definition of ready: The workload has an accountable owner, testable contract, known dependencies, target hypothesis, sanitized pilot inputs, and measurable acceptance gates. Resolve missing evidence before committing a migration date.

Production go/no-go: Require contract and negative-path tests, security approval, measured performance, monitored support ownership, recovery/replay evidence, a cutover checklist, rollback rehearsal, and business acceptance. Decommission only after the stabilization window and retention obligations are complete.

Questions that often change the answer

Can APIM replace all of MuleSoft?

No. APIM is a strong candidate for API gateway and management requirements. Flows, connectors, transformations, stateful orchestration, messaging, and batch work require other execution services. Preserve this distinction in scope, cost, staffing, and DR planning.

Should every Mule flow become a Logic App?

No. Logic Apps is a strong candidate for visual connector-based orchestration, but some flows should stay code-first, move to bulk-data tooling, become asynchronous, consolidate, or retire. Extremely chatty or latency-sensitive synchronous logic may fit a single coded service better.

Is Data Mapper a drop-in DataWeave replacement?

No. It is a visual transformation option with its own schemas, capabilities, and supported hosting experience. DataWeave modules, functions, type coercion, streaming, and edge cases require explicit analysis and golden-data tests; complex logic can move into a tested code component.

Can the old and new platforms coexist?

Yes, as an intentional migration pattern. A gateway can route to selected Mule backends while new implementations are validated. Coordinate identity, consumer contracts, telemetry, queue consumer ownership, and data consistency. Avoid double-processing writes during comparisons or rollback.

Does active-active APIM make the integration platform active-active?

No. Gateways, workflow execution, message stores, application data, private connectivity, and upstream dependencies have distinct availability and recovery models. Define state ownership, duplicate prevention, failover, and failback for the entire business transaction.
